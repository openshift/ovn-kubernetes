# Bridge Flows

## Introduction

OVN-Kubernetes programs OpenFlow rules on the external bridge (`breth0`) to
steer traffic between the physical network, OVN patch ports, and the kernel
(LOCAL port). This document describes the design decisions behind notable
flow sets on the bridge.

## ARP/NDP Fan-out Filter Flows

### Problem

When Cluster User Defined Networks (CUDNs) are enabled, each CUDN gateway
router (GR) has an external interface that shares the node's physical IP
address. On `breth0`, two mechanisms deliver incoming traffic to OVN patch
ports:

1. **Priority-10 fan-out rule** — replicates unicast traffic destined to the
   bridge MAC (`dl_dst=bridgeMAC`) to every patch port (default + all CUDNs).
2. **Priority-0 NORMAL fallback** — floods broadcast and multicast frames to
   all ports via normal L2 learning.

ARP requests for the node IP can arrive as:

- **Broadcast** (`dl_dst=ff:ff:ff:ff:ff:ff`) — initial resolution from a
  remote node.
- **Unicast** (`dl_dst=bridgeMAC`) — neighbor probes / reconfirmation from a
  remote node that already has an entry.

IPv6 Neighbor Solicitations arrive as:

- **Multicast** (`dl_dst=33:33:ff:xx:xx:xx`) — solicited-node multicast group.

In all three cases, every CUDN GR receives the request and generates a reply
(ARP reply or Neighbor Advertisement), because they all own the same node IP.
These duplicate replies flood the physical network and cause:

- Remote nodes passively learning redundant `MAC_Binding` entries.
- Elevated `ovs-vswitchd` CPU from processing the reply storm.

The impact scales linearly with the number of CUDNs. Each ARP request
produces N replies (one per CUDN GR + the default GR), and each reply
triggers OVN `MAC_Binding` resubmits on every remote node. In testing, with
just 70 CUDNs `ovs-vswitchd` CPU reached ~400% and packet drops were
observed due to the processing overhead.

### Solution

Priority-11 flows in table 0 intercept ARP requests (`arp_op=1`) and IPv6
Neighbor Solicitations (`icmpv6_type=135`) targeting any local node IP. The
match uses `arp_tpa` / `nd_target` without restricting `dl_dst`, so it covers
broadcast, unicast, and multicast cases in a single rule.

The action delivers the packet to exactly two destinations:

- **Default network patch port** — the default GR replies for the node IP (tagged,
  as OVN expects on VLAN setups).
- **LOCAL** — the kernel network stack can also respond (with `strip_vlan` in
  VLAN mode, since LOCAL is an untagged access port).

CUDN patch ports are excluded, preventing duplicate replies at the source.

### Example Flows

Non-VLAN mode (single-stack IPv4, node IP `172.18.0.3`):

```text
priority=11, table=0, arp, arp_op=1, arp_tpa=172.18.0.3, actions=output:<default-patch>,output:LOCAL
```

VLAN mode (dual-stack, VLAN 100, node IPs `172.18.0.3` and `fd00::3`):

```text
priority=11, table=0, dl_vlan=100, arp, arp_op=1, arp_tpa=172.18.0.3, actions=output:<default-patch>,strip_vlan,output:LOCAL
priority=11, table=0, dl_vlan=100, icmp6, icmpv6_type=135, nd_target=fd00::3, actions=output:<default-patch>,strip_vlan,output:LOCAL
```

### Code Reference

These flows are generated by `arpFanoutFilterFlows()` in
`go-controller/pkg/node/bridgeconfig/bridgeflows.go` and are installed only
when network segmentation is enabled (`IsNetworkSegmentationSupportEnabled()`).
